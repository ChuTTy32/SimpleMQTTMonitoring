# AGENTS.md — инструкции для агентов, работающих в этом репозитории

Этот файл читают AI-агенты (Claude Code и др.) в начале работы над задачами в репозитории
`SimpleMQTTMonitoring`. Он задаёт обязательный порядок работы, правила git и правила запуска
сервисов. Контекст по архитектуре, стеку и текущему статусу проекта — не здесь, а в
`docs/PROJECT.md`.

## Обязательный порядок работы

### В начале работы

1. Прочитать `docs/PROJECT.md` целиком — это единая точка правды по текущему состоянию
   проекта (архитектура, стек, статус модулей, ветки, известные расхождения с планом).
2. Если задача касается конкретной подсистемы — свериться с соответствующим доком
   (`docs/database-schema.md` для БД и т.д.), а не полагаться только на память из
   `PROJECT.md`, если он мог устареть.
3. Проверить `git status` и текущую ветку — в проекте бывают несмёрженные ветки с
   разошедшимся состоянием (см. предупреждения в `PROJECT.md`). Не считать `main`
   автоматически самым актуальным по всем подсистемам.

### В процессе / в конце работы

4. Если в ходе работы менялась архитектура, стек, статус модуля, схема БД, формат
   MQTT-топиков/сообщений или появлялись новые важные факты о проекте — **дописать**
   `docs/PROJECT.md`. Дописывать, а не переписывать целиком: обновлять релевантные разделы
   (`Статус по модулям`, `Ближайшие шаги`, конкретный раздел стека), не трогая то, что не
   менялось. Если правки крупные — можно обновлять по ходу работы, а не только в конце.
5. Если менялась структура модулей, зависимости между ними или потоки данных — запустить
   roadmap-skill (`docs/ROADMAP-SKILL.md`) для обновления `docs/codemap/`. Не запускать его
   по мелким правкам (опечатки, мелкий рефакторинг внутри модуля) — только когда меняется
   архитектурная картина.

## Git-правила

1. **Формат коммит-сообщений:** `тип: короткое предложение с описанием изменения на русском`.
   Пример: `fix: исправление парсинга файлов и загрузки данных из таблицы пользователей`.
   Допустимые типы: `feat`, `fix`, `update`, `refactor`, `test`, `docs`, `chore`.
2. **Коммитить без явного разрешения пользователя нельзя.** Даже если задача выполнена и
   изменения выглядят завершёнными — предложить коммит и подождать подтверждения, не
   создавать его самостоятельно.
3. Ветка на модуль (`module/0X-название`), PR обязателен даже для работы соло.
4. Никаких force-push, `git reset --hard`, перезаписи чужих веток без явного разрешения.

## Правила запуска сервисов

**Перед запуском любого модуля (брокер, БД, backend, frontend и т.д.) — сначала проверить,
не запущен ли он уже.** Двойной запуск ведёт к конфликтам портов и мусорным контейнерам.

- Проверить `docker ps` / `docker compose ps` перед `docker compose up`.
- Проверить занятость нужных портов (1883 для MQTT, 5432 для Postgres, порты API/фронта и
  т.д.) перед стартом сервиса вне Docker.
- Если сервис уже запущен и работает — не перезапускать его без необходимости; переиспользовать
  текущий инстанс для проверки поведения.

## Границы — что нельзя делать без явного разрешения

- Менять технологический стек подсистемы (уже был прецедент: фронтенд перешёл с Nuxt 4 на
  Vue 3 + Vite без фиксации решения — постфактум пришлось восстанавливать это по коду).
  Любая смена стека — явное решение пользователя, фиксируется в `PROJECT.md`.
- Сливать ветки в `main` (даже если конфликтов не предвидится).
- Удалять данные, тома с данными БД, любые файлы вне явной задачи.
- Коммитить и пушить (см. Git-правила выше).
