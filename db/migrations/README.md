# `db/migrations/` — схема БД

Единственный источник правды по схеме. Не принадлежит ни `api/`, ни `consumer/` —
см. `docs/PROJECT.md`, раздел «Миграции БД». Применяются одноразовым сервисом `migrate`
(`migrate/migrate`) из `docker-compose.yml`, вручную — `make migrate-up`.

## ⚠️ Правило: никаких «;» кроме конца оператора

Миграции выполняются с флагом **`x-multi-statement=true`** (см. строку `-database=...`
у сервиса `migrate` в `docker-compose.yml` и `DB_URL` в `Makefile`).

Флаг обязателен, потому что TimescaleDB запрещает
`CREATE MATERIALIZED VIEW ... WITH (timescaledb.continuous)` внутри транзакции, а без
флага golang-migrate отправляет весь файл одним simple query — Postgres оборачивает такой
пакет в неявную транзакцию, и миграция падает.

Плата за флаг: golang-migrate разбивает файл на операторы **наивно, по точке с запятой** —
он не понимает ни строковых литералов, ни комментариев. Поэтому:

- **нельзя** ставить «;» внутри `--` комментариев;
- **нельзя** ставить «;» внутри строк (`COMMENT ON ... IS '...'`);
- **нельзя** использовать `DO $$ ... $$` блоки и функции с телом на PL/pgSQL — точки с
  запятой внутри тела разорвут блок на куски.

Вместо «;» в прозе используй тире или точку. Если реально понадобится PL/pgSQL-блок —
выносить его в отдельный файл миграции и решать вопрос отдельно, а не «просто добавить».

Симптом нарушения — `pq: syntax error` или `unterminated quoted string` на куске текста
из комментария.

## Вторая плата: миграции не атомарны

С `x-multi-statement=true` операторы идут по одному, вне общей транзакции. Если файл упал
в середине — часть операторов останется применённой, а версия будет помечена `dirty`.
Чинится сбросом dev-базы: `make down-v && make up` (данные теряются, для dev это норма).
